# 需求与确认流程

## 分级但不强制安装流程工具

日常局部改动直接核实实现；中等行为/接口/权限变化先简述设计与验收；重大跨模块变化先范围、风险、拆分与回滚方案。
项目已有规格 / 变更管理流程（如 OpenSpec、RFC、设计文档）时沿用其唯一记录；没有就用项目已有计划，不为普通改动引入新流程工具或生成重复记录。
规划批准与实现授权区分，用户仅要求方案时不写业务代码。

## 必须确认

- 字段、枚举、权限码、状态流转和接口候选仍无法核实。
- 接口文档、需求文档、原型、截图、现有代码或用户口述之间任一不一致：动手改代码前先汇总成“来源 A 说 / 来源 B 说 / 影响”的清单交给用户，由用户修订源头并指定唯一基准，否则无法确定以什么为准编码与测试；设计值与项目 tokens 不一致且无法归并同样先确认。
- 设计未给出的状态在项目中没有可沿用模式；无设计稿界面的产品主题、受众或首要任务不明。
- 超限拆分涉及外部公共契约、大范围迁移或未授权模块。
- 后端数值 ID 与前端字符串硬规则在真实请求中不兼容。
- 新依赖、改变库/框架、提交/推送或删除非当前任务内容。

## 提问结构

事实：已经看到的代码/文档与来源。
未知：必须决定的唯一问题。
影响：两种答案对字段/交互/数据造成什么差异。
确认：请用户选择/提供正式契约。

不要问工具能直接查到的事实；不确定业务决定必须问。不要因为赶进度自行猜默认值，也不要在多份材料矛盾时挑一份“看起来最新”的直接开工。
等待确认时可以继续独立部分，但最终列明未决项，不称完成。

## 任务证据

输入来源 → 已确认行为 → 修改文件 → 测试断言 → 执行结果。
同一错误反复修两次未改善，停止扩张改动，建立更小复现和真实证据；不得第三次继续猜布局/接口。
未执行命令不写通过，未连接用户页面不称已验证用户实际环境。
