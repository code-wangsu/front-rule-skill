# API、mock 与 ID 契约

## 核实顺序

1. 搜索相邻 API wrapper 与调用链，确认是否可复用。
2. 查真实文档/接口详情；不能只看搜索摘要。来源记录为 doc-confirmed。
3. 没有正确接口或能力不可用时停止猜测，让用户提供路径、方法、请求字段、响应字段、枚举及分页结构；完整后标记 user-confirmed。
4. 契约冲突或缺失标记 pending；只能先做不依赖它的内容。
5. 不反复换关键词直到找到“像是对的”接口；多候选由用户确认。

## 接入顺序

未接入前：模拟数据集中在模块文件夹下的 `mock.js`（或项目既有 mock 约定），结构可贴近预期契约但不得被当作契约。
接入：契约确认 → 检查 mock 引用 → 删除该动作 mock / 拦截 / 死 import → API wrapper → 直绑响应 → 空态/错误/loading → 目标测试；模块全部接入成功后删除整个 `mock.js` 及所有引用，避免数据污染与无用文件；不删其它模块 mock，不把未知接口留成猜测实现。
生产代码禁止 api || mock、失败回退假数据、mock 字段兼容链。
单测可 stub 正式 API，不得把测试 fixture 当作真实后端结果。

## 原字段直绑

```js
/** 当前列表直接消费接口 page.records，不生成第二套行模型。 */
records.value = response.data.page.records
```

后端 records/title/ownerNames 等字段按实际契约直接使用。禁止 name→title、id→recordId 等无理由别名。
请求表单状态同名字段直接使用；禁止为同名字段写 normalize/build/map 仅逐项复制。
提交只包含对应动作允许字段，不能为了“直传”把 UI 状态、权限对象和服务器只读字段一并传入。
必要差异局部处理：日期范围组合控件拆多个参数、显示格式、已确认枚举、树结构、ID 字符串策略；说明证据与原因。

## ID 特例

- id、实体标识、关联 ID、路由 ID、ID 集合按 string/string[]；接口文档数值类型不改变这一前端策略。
- 数量、页码、金额、状态码没有实体标识语义时按原契约类型，不用后缀机械误判。
- 未填 ID 按契约省略/null/空串，不传 0/undefined 字符串。
- 输入本来是字符串时原样传递；只有安全整数 Number 可在确认来源后显式 String，禁止接受不安全数值并伪修复。
- 后端大整数 JSON 数字由原生 JSON.parse 解析会丢精度；要求后端改为 JSON 字符串。只有用户明确批准且核实 JSON 解析库时才讨论特殊无损解析，不擅自加依赖。
- 后端实测拒绝字符串请求时停止并确认兼容方案，不用数值转换掩盖冲突。
- 测试样例：'9007199254740993'、'9223372036854775807'，请求、缓存、选中值和路由前后逐字一致。

## API wrapper

使用项目统一 HTTP 客户端，baseURL、method、data/params 以契约与封装为准；页面不手写 URL/axios。
API 层只做请求：一个接口一个函数，透传调用方参数、返回客户端响应；不在 API 文件内做字段映射、参数拼装、格式化或业务判断，需要的差异处理放在调用方 hooks / 具名纯函数并写明依据。
提示去重：先读拦截器实现，确认成功 / 失败时是否已统一弹出；接口响应携带提示文案时以接口文案为准，业务层不再追加，避免同一动作显示两次。接口与拦截器都不提示时，前端按功能语义补充一次提示。finally 释放 loading，失败不得继续执行成功流程。
只读请求防乱序；关闭浮层使旧请求失效；提交禁重复并必要时有确认，不擅自并发 CRUD。
后端数据不可用时展示错误/空态，不制造“看上去正常”的结果。
